# 这套系统是怎么搭的

一个佛典检索问答界面。回答由本地 GPU 上的大模型生成，依据来自存在分布式存储里的语料库 —— 没有一次请求离开这台集群。

## 一次提问经过的地方

```
浏览器
  │  SSE（断线可重连，只补差量）
webui ──ACP──▶ hermes agent
  │                 │  MCP over HTTP
  │                 ▼
  │            memory-mcp ──▶ autumn（BM25 + 向量索引）
  │                                   ▲
  └──OpenAI 兼容 API──▶ FreeToken ─────┘
                          │  权重经 FUSE 挂载读取
                        RTX 4090
```

## 四个部件

### FreeToken · 单张 4090 跑 MoE 大模型

模型是 **DeepSeek-V4-Flash**，一个混合专家（MoE）模型。它的完整权重 155 GiB，而一张 4090 只有 24 GiB 显存 —— 装不下。

FreeToken 的做法是**把路由专家放在宿主内存里，一部分在 CPU 上算**。于是限制模型规模的不再是显存，而是内存：稠密部分常驻 GPU，专家按需取用。代价是权重从「常驻问题」变成了「冷启动流式读取问题」—— 这正好是下面那层擅长的事。

### autumn · 存储层

自研的分布式存储，同时承担两件事。

**存模型权重。** 155 GiB 的检查点放在 autumn 里，通过一个 FUSE 挂载读出来。冷启动时八个读线程并发拉取，实测约 430 MiB/s，六分半读完。

**存语料与索引。** 这是更有意思的部分：**倒排索引本身就是普通的 KV 记录**，没有独立的索引文件、没有嵌入式数据库。

```
idx/{词}/{文档}    → 空值，纯粹是"存在标记"
doc/{文档}         → 权威记录：词频、原文、元数据
ivf/{质心}/{向量}  → 向量倒排桶
```

候选发现是一次**只扫 key 不读 value** 的范围扫描，BM25 打分在客户端算。重新索引时留下的陈旧标记会被自动忽略 —— 因为权威记录才是正确性边界，标记只是线索。

### memory-mcp · 检索服务

把语料库以 **MCP over HTTP** 暴露给 agent。它同时提供 REST 和 MCP 两个面，共用一套工具实现。

选 HTTP 而不是 stdio 是有代价考量的：stdio 的 MCP 服务器必须由客户端**拉起进程**，那意味着每个消费者都要带上这个二进制、它的存储凭据和生命周期。走 HTTP，这个依赖就只是一个地址。

检索有三条腿：**BM25 词法**（含中日韩双字切分）、**IVF 向量**、**图遍历**。

### hermes + webui · 对话层

hermes 是 agent 运行时，通过 ACP 协议以子进程方式驱动。webui 只做两件事：会话管理和对话框。

一个刻意的设计：**一轮对话属于服务端，不属于这个页面**。回答在服务端自己的任务里生成，写进一个带序号的缓冲区；浏览器只是订阅者。所以刷新页面、关掉标签页、换个窗口打开，那一轮都在继续，重连时只补上错过的部分。

## 中文检索的一个细节

查「慧能」时，把它拆成「慧」和「能」两个字会出问题：「能」几乎每篇文档都有，BM25 会把结果排给用词最多的那篇 —— **六祖的名字，检索不到他自己那部经**。

所以索引时除了单字，还会额外生成**相邻双字**：「慧能」本身也是一个词项，它足够罕见，于是在短语查询上占主导，而单字仍然服务于「猫」「佛」这类单字即词的查询。

双字词项**不计入文档长度** —— BM25 按长度归一化，让中文文档贡献双倍长度会让它在混合语料里被系统性地压低。
